## 1 引言

### 1.1 编写目的

本计划用于界定“智能共享自习室预约系统”的测试范围、测试策略、资源安排、进度与准入/准出标准，作为各模块测试执行（见《系统测试报告》SSR-TEST-001）与测试用例设计（见《测试用例》SSR-TC-001）的权威指导基准。

预期读者：项目组长、各模块全栈开发与测试负责人、课程设计指导教师。

### 1.2 项目背景

本项目为《系统分析与设计》课程设计课题，由 5 人敏捷开发小组自主研发，采用“5 大功能模块垂直全栈分工”模式。各成员不仅承担各自功能模块的前端交互视图、后端领域逻辑与数据库/缓存开发，同时担任该模块的质量测试负责人，实施全流程测试闭环。系统整体采用 Go 1.27 + Gin 核心服务、Vue 3 + Vite 前端架构、PostgreSQL 18 主数据库与 Redis 7 缓存/分布式互斥层。系统架构与模块边界详见《概要设计说明书》SSR-HLD-001 与《详细设计说明书》SSR-DD-001。

## 2 测试目标与范围

### 2.1 测试目标

围绕 5 大功能模块垂直全栈划分，确立系统测试目标如下：

1. **模块一（用户与权限）**：验证 JWT 鉴权体系、BCrypt 密码哈希、RBAC 角色隔离（学生/管理员）以及用户登出后的 Redis 黑名单（`studyroom:auth:blacklist:*`）即时拦截机制；
2. **模块二（座位与预约）**：验证座位平面图数据渲染、智能自动分配加权算法、预约生命周期六态不可逆流转，以及多用户并发抢座时 Redis 分布式互斥锁（`studyroom:lock:seat:*`）与 PostgreSQL GiST 物理排除约束（`excl_seat_overlap`、`excl_user_overlap`）的“绝不超卖”零脏写特性；
3. **模块三（信用与候补）**：验证信用积分奖惩流水记录、低信用履约受限拦截、满座先到先得候补排队登记、实时位次计算与站内通知已读状态机流转；
4. **模块四（统计与可视化）**：验证运营指标聚合统计 API、空间占用热力图矩阵计算、Redis 旁路缓存（`studyroom:cache:stats:*`）叠加 ±10% Jitter 防雪崩机制，以及 3D 座位探索前端分包构建；
5. **模块五（AI 助手与运维）**：验证 OpenAI 兼容 SSE 流式对话、座位推荐结果二次核验、Redis 接口限流中间件（`studyroom:ratelimit:*`）、后台定时巡检调度器 Leader 选举（`studyroom:scheduler:leader`）与健康探针；
6. **工程与构建质量**：验证前端 Vite 生产构建顺利通过，无阻断性编译异常。

### 2.2 测试范围

**纳入测试范围**：

| 层次 | 覆盖模块与对象 | 主要验证特性 |
| --- | --- | --- |
| 单元测试（22项） | 模块一、模块二、模块四、模块五 | 智能分配算法、时段校验边界、分布式锁属主与看门狗、旁路缓存防雪崩、JWT注销黑名单、接口限流中间件、AI客户端、配置严格解析 |
| 接口端到端（23项） | 模块一至模块五（全模块覆盖） | 系统健康探针、用户鉴权与RBAC、房间座位图、预约创建/互斥/取消、候补登记/排队/退出、信用流水、站内通知、热力图矩阵、注销黑名单 |
| 并发压力测试（3项） | 模块二（座位与预约） | 20 独立学生线程瞬时抢占同一座位时段，采集互斥阻断率与 P95 响应耗时 |

1. 浏览器全矩阵兼容性（仅在主流 Chromium 内核 Chrome/Edge 最新稳定版进行人工验证）；
2. 移动端真机物理适配；
3. 真实外部商业网关（第三方商业短信、微信公众号通知——系统架构上采用站内信解耦，不依赖外部网关）；
4. 第三方大语言模型底层输出内容的情感与政治合规性（仅验证 OpenAI 协议交互兼容性、流式拼装及降级处理）。

## 3 测试策略

### 3.1 总体策略

系统严格遵循“三层测试”金字塔体系，从单元层向外逐步推进至业务端到端与极值并发场景：

```text
┌─────────────────────────────────────────────────────────────┐
│  第 3 层：并发与性能测试（压测层）                            │
│  - Python concurrent.futures 20 线程瞬时突发抢座              │
│  - 验证 Redis 互斥锁 + PostgreSQL GiST 排除约束“绝对防超卖”   │
├─────────────────────────────────────────────────────────────┤
│  第 2 层：接口端到端集成测试（E2E 业务闭环层）                 │
│  - Python 原生 urllib 驱动 23 项全业务流 HTTP 断言           │
│  - 覆盖游客/学生/管理员三种身份，验证状态机与数据持久化       │
├─────────────────────────────────────────────────────────────┤
│  第 1 层：核心算法与组件单元测试（白盒单元层）                 │
│  - Go 官方 testing + 表驱动模式 + miniredis 内存模拟         │
│  - 验证纯函数确定性计算、边界值防御、并发锁属主与降级容错     │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 各层策略说明

#### 3.2.1 单元测试策略
- **工具框架**：Go 官方标准库 `testing`，采用参数化表驱动（Table-Driven）设计模式；
- **内存替身**：Redis 外部依赖采用 `alicebob/miniredis/v2` 进行内存 Mock，保证单元测试在无外部服务环境下依然具备 100% 可重复性与毫秒级执行性能；
- **测试重点**：加权分配评分排序算法、预约时段边界与粒度校验、分布式锁 UUID 属主释放校验与自动续租、缓存抖动防雪崩算法、IP/用户令牌桶限流算法；
- **分工机制**：各模块全栈开发负责人对自己主责的领域算法与中间件编写对应的单元测试代码。

#### 3.2.2 接口端到端测试策略
- **工具框架**：基于轻量级自动化测试脚本 `scripts/test_api_e2e.py`，全量采用 Python 3 标准库（`urllib.request`），无需引入外部复杂工具；
- **测试范围**：覆盖全系统 5 大模块、23 项关键端到端场景，包括正向预约流转、逆向越权阻断、跨时段重叠冲突拦截、候补自动递补及黑名单生效拦截；
- **数据机制**：依赖标准测试种子数据（系统预置管理员 `admin/admin123` 及学生用户 `stu01`~`stu40`），每个断言独立执行，确保测试异常不中断。

#### 3.2.3 并发与性能测试策略
- **工具框架**：自动化并发测试脚本 `scripts/test_concurrency.py`，采用 Python `concurrent.futures.ThreadPoolExecutor` 构造 20 线程突发并发；
- **身份凭据**：脚本内置利用 `hmac-sha256` 算法直接离线签发 20 个独立合法的学生 JWT，绕过登录接口限流中间件，保证瞬时毫秒级突发请求到达后端；
- **验证断言**：成功数严格为 1，冲突拦截数严格为 19，服务异常 5xx 严格为 0；
- **环境自洁**：并发测试完毕后，测试脚本调用取消接口自动释放该预约，维持自习室座位状态干净。

### 3.3 测试类型矩阵

| 测试类型 | 执行状态 | 责任模块 | 重点说明 |
| --- | :---: | --- | --- |
| 功能测试 | **是** | 模块一~模块五 | 由 E2E 接口测试完整覆盖 23 项业务场景 |
| 边界值测试 | **是** | 模块二（座位与预约） | 时段边界：整 8 小时上限、8.5 小时超限、15 分钟非法粒度、起止时间相等/倒置 |
| 异常与安全测试 | **是** | 模块一（用户与权限） | RBAC 越权拦截（403）、错误凭证拦截（401）、登出令牌黑名单即时拦截 |
| 并发互斥测试 | **是** | 模块二（座位与预约） | 20 线程瞬时并发抢占同一座位，验证分布式互斥与数据库排他约束 |
| 性能与延时测试 | **是** | 模块五 / 全体 | 采集并发场景下的 Min、Avg、P95 与 Max 响应延时 |
| 容错降级测试 | **是** | 模块五（AI与运维） | 验证 Redis 离线时限流中间件、缓存组件及分布式锁的安全降级策略 |
| 构建发布验证 | **是** | 模块四（可视化） | 前端 Vite 生产构建与页面路由分包完整性检查 |
| 浏览器兼容测试 | **否** | — | 本阶段仅在最新版 Chrome/Edge 上人工走查，不展开多浏览器矩阵 |

## 7 风险与应对措施

| 风险项 | 潜在影响 | 预防与应对措施 |
| --- | --- | --- |
| 测试环境 Redis 服务未启动或异常 | 限流、分布式锁与黑名单用例失败 | 执行测试前先运行 `docker compose ps` 确认容器健康；单元测试层采用 `miniredis` 隔离依赖 |
| 本地开发宿主端口冲突（8080/5433/6380） | 服务无法启动或测试脚本连错环境 | 统一通过 `.env` 中的 `STUDYROOM_HOST_PORT` 灵活调整宿主映射端口，脚本常量同步适配 |
| 测试脚本基准端口与 Docker 映射不符 | E2E 用例全红或网络超时 | 启动测试前执行端口连通性探针，或在脚本中引入环境变量动态获取基准地址 |
| 测试过程中种子数据被并发用例修改污染 | 影响后续用例的断言结果 | 并发抢座脚本内置自动清理逻辑；支持一键重置：`docker compose down -v && docker compose up -d` |
| 外部大模型 API 密钥未配置或网络抖动 | AI 助手功能调用受阻 | 系统针对 AI 模块设计了优雅降级机制，未配置 Key 时不影响自习室预约等核心业务运行 |
| 高并发测试后残留测试预约单 | 污染历史统计与座位占用状态 | 并发测试脚本结束时通过自动化 Hook 执行取消预约清理，保证数据库状态幂等整洁 |
