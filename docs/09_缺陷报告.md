## 1 说明

### 1.1 编写目的

本报告记录在单元测试、接口端到端测试、高并发抢座压测、前端生产构建与代码审查过程中发现的缺陷、风险与演进优化项，并基于“5 大功能模块垂直全栈分工”体系跟踪其处理状态与责任闭环，作为系统软件质量评估与后续版本迭代的证据。

### 1.2 缺陷分级定义

| 级别 | 名称 | 判定标准 | 处理要求 |
|:---:|:---:|---|---|
| **A** | **致命** | 导致系统崩溃、数据破坏超卖、安全鉴权沦陷或核心功能不可用 | 必须立即修复，未关闭不可交付 |
| **B** | **严重** | 主要功能异常或存在明确安全隐患，但具备兜底或降级机制 | 必须修复或给出经评审明确的设计约束缓解方案 |
| **C** | **一般** | 次要功能缺陷、交互体验问题、非功能性偏差或文档不一致 | 计划内修复并进行回归验证 |
| **D** | **建议** | 部署灵活性、代码质量、工程效率与可维护性优化建议 | 记录进入后续版本演进储备池 |

### 1.3 缺陷状态定义

- `已修复`：缺陷根因已定位并修改代码/文档，通过回归测试验证闭环；
- `已缓解（设计约束）`：基于开发期联调或高可用容灾考量所做出的有意识工程权舍，已在设计文档中明确约束并覆盖降级测试；
- `已知限制（不修复）`：属于课程设计教学演示范围内的配置约定或打包体积建议，不影响业务功能闭环；
- `待排期`：功能演进类优化建议，登记于后续迭代规划。

### 1.4 统计口径说明

本报告的所有缺陷均来源于自动化测试输出、前端构建编译告警、跨模块权限联调记录及严格的代码/文档一致性审查，**不包含无法复现或未经核实的偶发猜测**。

## 3 缺陷明细（8 项）

### BUG-001 CORS 允许任意来源（B 严重）

| 属性 | 内容详情 |
| --- | --- |
| **缺陷编号** | BUG-001 |
| **归属模块** | 模块一：用户与权限模块 / 模块五：运维安全 |
| **发现阶段** | 安全代码审查 |
| **报告人** | 王建东（nightsky5819，模块五负责人） |
| **修复责任人** | 赵晨曦（imicola，模块一负责人）/ 王建东（nightsky5819） |
| **关联代码** | `backend/internal/middleware/cors.go` |
| **缺陷描述** | 中间件当前固定返回 `Access-Control-Allow-Origin: *`，任意第三方站点均可携带用户凭据发起跨域请求。 |
| **复现路径** | 审查 `cors.go` 第 13 行：`c.Header("Access-Control-Allow-Origin", "*")`。 |
| **潜在影响** | 教学与本地联调环境可完全接受；若未来直接面向公网部署，存在跨站请求伪造等安全滥用隐患。 |
| **处理结果** | **已缓解（设计约束）**：开发期为保障前端 Vite 开发服务器（端口 5173）与各类测试脚本顺畅联调而有意保留。已在《需求规格说明书》7.1 节与《概要设计》第 8 章明确标明“正式生产环境需收紧为域名白名单”。 |
| **后续建议** | 将允许跨域的来源配置化，通过 `.env` 注入白名单列表，生产环境默认拒绝非白名单域名。 |

### BUG-002 JWT 黑名单查询失败时降级放行（B 严重）

| 属性 | 内容详情 |
| --- | --- |
| **缺陷编号** | BUG-002 |
| **归属模块** | 模块一：用户与权限模块 |
| **发现阶段** | 中间件白盒测试与高可用审查 |
| **报告人** | 王建东（nightsky5819，模块五负责人） |
| **修复责任人** | 赵晨曦（imicola，模块一负责人） |
| **关联代码** | `backend/internal/middleware/auth.go` |
| **缺陷描述** | 鉴权中间件在校验令牌黑名单时，若 Redis 查询发生网络超时或离线错误，仅记录告警日志并默认放行请求（第 34—37 行），意味着在 Redis 故障期间已注销的失效令牌仍可能短时通过校验。 |
| **复现路径** | 停止 Redis 实例后，携带已调用 logout 的旧 Token 访问受保护 API。 |
| **潜在影响** | 属于高可用性与强安全性之间的工程权衡：优先避免 Redis 偶发抖动导致全站鉴权雪崩，代价是短时内注销凭证拦截存在时间窗口。 |
| **处理结果** | **已缓解（设计约束）**：属于有意识的高可用容灾降级策略，系统留有完备的告警日志；在测试用例 TC-U02 中已覆盖“黑名单读取失败安全上报与服务降级”断言。 |
| **后续建议** | 增加进程内本地短期 LRU 缓存，或在高敏感管理接口上配置“Redis 离线即拒绝”严格安全策略。 |

### 4.1 按 5 大业务模块分布统计

| 2 | **模块二：座位与预约模块** | **0** | — | 核心预约引擎、状态机流转与 20 并发防超卖互斥在设计与测试中实现**零缺陷** |
| 3 | **模块三：信用与候补模块** | **0** | — | 信用奖惩流转、满座候补排队与站内通知机制经 E2E 完整覆盖，实现**零缺陷** |
| 4 | **模块四：统计与可视化模块** | **2** | BUG-003, BUG-008 | 涉及前端 WebGL/Three.js 分包体积告警与大屏页面访问权限口径对齐 |

### 4.2 质量评估归因

1. **核心业务架构健壮**：自习室座位预约与并发互斥作为系统最关键、最复杂的业务，在本次测试中实现 0 缺陷，说明 Redis 分布式锁 + PostgreSQL GiST 物理排他约束的技术选型非常有效；
2. **严重缺陷全部得到合理缓解**：CORS 策略与黑名单降级放行均属于教学联调与服务可用性保障的有意识工程取舍，系统均有完备的日志审计与设计约束；
3. **文档与规范缺陷全面清零**：历史遗留的重复段落、历史占位账号及单一流水线旧角色称谓已随本轮重构 100% 修复闭环；
4. **工程演进方向清晰**：打包体积优化、动态脚本环境变量等已形成明确的后续迭代路线。
