# 1 系统概述

## 1.1 现状描述

随着考研、考证与终身学习需求的增长，高校图书馆与付费自习室面临持续的"一座难求"。对某高校图书馆的实地调研与访谈显示，传统自习室管理存在五个突出问题：

1. **信息不透明**：学生无法提前获知空位分布，"到馆找座"平均耗时 10 分钟以上，高峰期更甚；
2. **占座严重**：以物品占座造成"名义占用、实际闲置"，真实利用率被进一步压低；
3. **爽约无成本**：口头预约或简单登记后不到场无任何约束，座位被无效锁定整个时段；
4. **管理粗放**：管理员缺乏数据支撑，无法量化各时段、各区域的利用情况，排班与开放决策凭经验；
5. **分配低效**：高峰期人工引导排队秩序混乱，体验差且易生纠纷。

## 1.2 系统目标

本系统定位为"面向共享自习室的一站式座位预约与运营平台"，总目标是将座位资源**在线化、公平化、数据化**。分解为七个可度量目标（G1~G7）：在线预约、智能分配、全生命周期管理、信用治理、满座候补、数据可视化、消息通知（详见《需求规格说明书》2.1 节）。

## 1.3 系统开发方法

- **分析与设计方法**：面向对象分析与设计（OOA/OOD），以用例驱动需求、以领域模型驱动设计，产出用例图、类图、ER 图、状态图、时序图、数据流图等全套 UML/结构化模型；
- **过程模型**：增量模型。按"基础设施 → 认证 → 资源管理 → 预约核心 → 智能分配 → 治理机制（信用/候补/通知）→ 统计分析 → 前端集成"的顺序分八个增量交付，每个增量均可运行、可验证；
- **工程实践**：Git 分支协作（feature 分支 + 组长审查合并）、GitHub Actions 持续集成、表驱动单元测试、迁移脚本管理数据库演进。

## 3.2 代码设计

- **命名规范**：Go 标准驼峰；数据表/字段 snake_case；JSON 字段与数据库列名对齐，降低映射成本；
- **状态码设计**（预约状态机六态、座位三态、候补四态、账号两态、角色两态），全部以 CHECK 约束固化在数据库层；
- **错误码设计**：统一响应 `{code, message, data}`，HTTP 语义映射（400 参数 / 401 认证 / 403 权限或禁约 / 404 不存在 / 409 冲突 / 500 内部）；
- **来源标识设计**：预约 source ∈ {manual, auto, waitlist}，为统计与审计提供数据血缘。

## 3.5 算法设计

**自动分配评分模型**（完整流程图如下）：

【插图位置：diagrams/14_自动分配算法流程图.mmd —— 图 3-11 自动分配算法流程图】

> 总分 = 偏好匹配分（区域 30 + 电源 25 + 靠窗 15）− 近 7 日利用率 × 20 + 随机扰动 (0,1)

设计意图：偏好项保证个性化匹配；**热度均衡因子**将人流分散到低使用率座位，削峰填谷，提升整体资源利用均衡度；微扰避免所有人涌向同一"最优"座位。评分函数实现为无副作用纯函数（ScoreCandidates），可直接单元测试。

**热力图聚合算法**：generate_series 按房间开放时间生成与查询日期对齐的小时轴，对每个"座位×小时"格子以 EXISTS + tsrange 重叠判定占用，Go 侧组装矩阵并计算小时利用率（见详细设计 3.9 与图 3-12）。

## 3.6 输入输出设计

**输入**：全部表单（注册/登录/房间/座位/预约偏好/候补）均有前端校验（必填/长度/格式）与后端校验（binding 标签 + 业务规则）双重防护；时段输入统一 30 分钟粒度。

| 手动预约闭环 | 选座→预约→（窗口内）签到→离开→返回→签退 | ✅ 状态 pending→checked_in→temp_leave→checked_in→completed，时间戳齐全，信用 +1 |

# 5 收获和体会

## 5.1 小组总结（组长撰写）

本次课程设计历时 18 天，小组按计划完成全部四项核心功能与五项扩展功能，交付可运行系统、5 份文档、18 张分析设计图与 60 余次结构化提交，端到端测试与 CI 全部通过。达成情况：

1. **文档与代码高度一致**：数据字典、状态机、算法公式与实现逐项对齐，报告中的实测数据均可复现（种子数据可重放）；
2. **架构决策有效**：分层结构使五人并行开发零冲突合并；数据库排除约束两次在并发场景兜底拦截了应用层漏检的冲突；
3. **过程数据**：累计代码约 6200 行（后端 ≈3600，前端 ≈2600），测试用例 13 组，修复缺陷 1 个（测试驱动发现）。

## 5.2 开发体会（每人一份）

**成员一（组长，imicola）**：最大收获是"约束前置"——把业务规则（时段不重叠）下沉到数据库排除约束后，应用层只需处理语义转换，系统在并发下的正确性有了兜底。统筹五人协作让我体会到接口先行约定（概要设计 4.2 节的内部接口表）对并行开发效率的决定性作用。

**成员二（Glassous）**：实现信用分时最初想直接 UPDATE 分数，后来改为"单事务：分数夹紧 + 流水 + 禁约判断"后，才真正理解事务边界设计对数据一致性的意义。bcrypt 与 JWT 的组合让我第一次完整落地了无状态认证。

**成员三（DonGKids）**：调度器的批量状态迁移改用"条件 UPDATE + RETURNING"后天然幂等，重入无害——这让我理解了为什么定时任务要按"声明目标状态"而不是"执行动作"来设计。评分算法做成了纯函数，单测写起来非常顺畅。

**成员四（hjsdjuhv8）**：座位平面图从"表格"改为"网格矩阵 + 状态着色"后，演示效果质变；我体会到前端的价值不只是实现功能，而是把系统分析里的状态机翻译成用户一眼能懂的视觉语言。ECharts 热力图的矩阵→三元组转换踩了小坑，加深了对数据结构的理解。

**成员五（nightsky5819）**：写 TC-V09 时"顺手"输入了 "9:00"，没想到 Go 的 time.Parse 竟然宽容接受，这个缺陷如果上线会成为脏数据入口。测试左移当天发现、当天修复，成本几乎为零——这是我对"质量内建"最直观的一次体验。

## 5.3 待改进之处

1. **通知渠道单一**：目前仅站内通知，可扩展邮件/企业微信 Webhook；
2. **签到凭证弱**：靠时间窗口 + 账号操作，可引入座位二维码扫码签到防代签；
3. **统计实时性**：热力图为按需聚合，数据量大后应引入物化视图或预聚合表；
4. **部署形态**：当前为单机用户级集群演示，生产化需要容器编排与读写分离；
5. **前端体验**：Element Plus 全量引入导致构建产物偏大（>1MB），可改为按需引入与路由级代码分割。
