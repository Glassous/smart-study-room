# 1 系统概述

## 1.1 现状描述

随着考研、考证与终身学习需求的增长，高校图书馆与付费自习室面临持续的“一座难求”。对某高校自习空间的实地调研与访谈显示，传统自习室管理存在五个突出痛点：

1. **信息不透明**：学生无法提前获知空位分布，“到馆找座”平均耗时 10 分钟以上，高峰期更甚；
2. **占座严重**：以物品占座造成“名义占用、实际闲置”，真实利用率被进一步压低；
3. **爽约无成本**：口头预约或简单登记后不到场无任何约束，座位被无效锁定整个时段；
4. **管理粗放**：管理员缺乏数据支撑，无法量化各时段、各区域的利用情况，排班与开放决策凭经验；
5. **分配低效**：高峰期人工引导排队秩序混乱，体验差且易生纠纷。

## 1.2 系统目标

本系统定位为“面向共享自习室的一站式座位预约与运营平台”，总目标是将座位资源**在线化、公平化、数据化**。分解为七个可度量目标（G1~G7）：在线预约、智能分配、全生命周期管理、信用治理、满座候补、数据可视化、消息通知（详见《需求规格说明书》2.1 节）。

## 1.3 系统开发方法

- **分析与设计方法**：面向对象分析与设计（OOA/OOD），以用例驱动需求、以领域模型驱动设计，产出用例图、类图、ER 图、状态图、时序图、数据流图等全套 UML/结构化模型；
- **分工模式**：全面推行**「5 大功能模块垂直全栈分工」**体系。团队彻底打破传统的水平流水线分工壁垒，5 位成员分别担任模块一至模块五的主责负责人，在各自业务领域内端到端完成前端交互组件、后端微服务 API、数据库持久化与 Redis 缓存优化、单元/集成测试以及对应设计文档编写，实现特性闭环与高效并行迭代；
- **过程模型**：增量模型。按“基础设施与架构基线 → 用户认证与鉴权 → 座位资源与预约核心 → 信用治理与候补队列 → 运营统计与热力图大屏 → AI 助手与高可用运维 → 跨模块全栈联调与自动化测试”的节奏进行 15 天敏捷迭代；
- **工程实践**：Git 分支协作（feature/* 分支 + 组长代码审查合并）、GitHub Actions 持续集成、三层自动化测试金字塔（22 单测 + 23 接口测试 + 20 并发压测）、数据库声明式迁移脚本（`migrations/`）与 Docker Compose 容器编排。

**非功能性需求**：
- **安全性**：用户口令采用自适应哈希算法 bcrypt(cost=10) 单向散列，数据库不存任何明文口令；SQL 全量参数化执行以免疫 SQL 注入；基于 JWT Claims 的 RBAC 角色越权严格拦截；登出 Token 写入 Redis 黑名单即刻失效；
- **并发与防超卖性能**：高并发选座在 Redis 分布式锁与 PostgreSQL GiST 排除约束保护下，确保并发争抢时超卖数为 0；20 线程瞬时并发抢座实测 P95 响应时间控制在 191 ms 以内；常规接口响应时间 P95 < 300 ms；
- **可扩展性与适应性**：房间行列规模 1~30 行列自由配置；数据库连接、端口、密钥等全部通过环境变量注入，支持多环境无缝迁移。

## 2.3 业务流程分析

以系统最核心的“选座/智能推荐—抢占—签到使用—释放—候补递补”完整闭环为例（包含智能分配分支、违约惩戒分支与候补回流机制）：

【插图位置：diagrams/04_业务流程图_预约.mmd —— 图 2-2 预约业务流程图】

全链路流程要点：
1. **准入控制**：预约发起前由模块一检查 JWT 有效性与黑名单，由模块三校验信用分是否禁约；
2. **三层互斥抢座**：由模块二在毫秒级依次通过 Redis 分布式互斥锁预占、应用层重叠预检以及 PostgreSQL GiST 物理排除约束严格拦截并发冲突；
3. **履约监督**：签到窗口为开始前后 15 分钟，超时未到由模块五调度器自动置为 `violation`，触发模块三信用扣减；
4. **资源回流**：座位因签退、取消或违约释放时，触发模块三候补递补引擎，将空位分配给先到先得的排队学生并推送通知，实现自习资源的循环利用。

### 1. 偏好加权智能自动分配算法（模块二：座位与预约模块，叶泳言）

【插图位置：diagrams/14_自动分配算法流程图.mmd —— 图 3-11 自动分配算法流程图】

加权评分函数实现为无副作用纯函数 `ScoreCandidates`：
总分 = 偏好匹配分（区域 30 + 电源 25 + 靠窗 15）− 近 7 日利用率 × 20 + 随机扰动 (0, 1)
- 区域匹配度符合加 30 分，电源匹配加 25 分，靠窗匹配加 15 分；
- **热度均衡因子（$-20 	imes U_{7d}$）**：引入近 7 日座位历史平均利用率进行负向加权，同等偏好下优先分配冷门低频座位，实现人流在自习室空间维度的“削峰填谷”；
- 随机微扰项 $[0, 1)$ 打破同分僵局，算法单测通过率 100%。

### 2. 空间占用热力图矩阵聚合算法（模块四：统计与可视化模块，邹字）

【插图位置：diagrams/17_热力图数据流程图.mmd —— 图 3-12 热力图数据流程图】

利用 SQL `generate_series` 按开闭馆时间动态生成连续 1 小时时间步长序列，利用 `tsrange` 范围重叠操作符精准判定各座位在该小时的占用状态，Go 端组装二维矩阵；辅以 Redis 旁路缓存与 ±10% Jitter 随机抖动打散过期时间，彻底杜绝缓存雪崩。

### 3. 信用分奖惩流转与递补算法（模块三：信用与候补模块，姜文东）
构建 `ApplyDelta` 事务闭环，将信用变更与流水写入置于同一原子事务；满座候补采用 `created_at ASC` 严格保序，队首因突发时段冲突自动顺延不阻塞后续队列。

### 4. AI 业务上下文组装与卡片核验、高可用调度器（模块五：AI 助手与运维模块，王建东）

在本次课程设计中，我承担了全系统最为核心的业务中枢——模块二（座位与预约模块）的端到端全栈研发，涵盖自习室与座位建模、批量生成算法、平面图动态渲染、预约引擎、六态有限状态机、偏好加权自动分配算法以及高并发防超卖互斥方案。

研发过程中最具挑战性的技术攻关当属“高并发抢座防超卖体系”的构建。自习室选座属于典型的瞬时并发争抢场景，如果仅依赖数据库事务容易造成锁争用甚至死锁，而如果仅靠应用层缓存锁在网络抖动时极易超卖。为此，我设计了“三层并发互斥防御体系”：
1. 第一层在 Redis 层采用基于 `SET NX EX 30` 的细粒度互斥锁（`studyroom:lock:seat:<id>:<date>`），配合后台看门狗（Watchdog）每 10 秒自动续期，并在释放锁时通过 Lua 脚本比对 UUID Token 原子解锁，防止业务执行慢误删他人锁；
2. 第二层在应用层进行只读冲突预检，快速剔除明显重复的请求；
3. 第三层在底层 PostgreSQL 物理层启用 `btree_gist` 扩展，建立了双重 GiST 排除约束（`excl_seat_overlap` 与 `excl_user_overlap`），利用物理索引彻底堵死并发时段重叠的可能。在 20 线程并发瞬时抢座压测中，实测实现“严格 1 笔请求写入、19 笔冲突拦截、0 超卖”，平均响应时间仅 108.14 ms，P95 仅 190.86 ms，性能与安全性令人振奋。

此外，我设计了预约六态有限状态机（`pending` ⇄ `checked_in` ⇄ `temp_leave` → `completed` / `cancelled` / `violation`），并在自动分配算法中创新引入了“热度均衡因子（$-20 	imes U_{7d}$）”，在满足学生座位偏好的同时将人流引导至低频冷门座位，有效提升了自习室整体资源的利用均衡性。这次全栈实践让我深刻认识到底层数据库物理约束与分布式锁协同运用的巨大威力，工程视野得到了质的跃升。

### 5.2.3 姜文东（学号：2404060307，主责模块三：信用与候补模块）

在智能共享自习室系统中，我主责模块三（信用与候补模块）的垂直全栈研发，聚焦于自习室诚信生态治理、违约惩戒与履约激励、满座排队候补引擎与事件驱动型站内通知系统。

传统自习室“占座不来、违规零成本”是长期困扰运营管理的顽疾。为此，我构建了一套严谨的校园信用积分闭环治理体系：学生初始拥有 100 分，正常履约签退奖励 1 分，临近开始撤约扣减 2 分，超时未到违约扣减 8 分；一旦信用分低于 60 分，系统触发禁约逻辑，自动封禁 3 天预约与排队权限。在技术实现上，我设计了 `ApplyDelta` 事务处理方法，将分值更新、禁约检查与 `credit_logs` 流水插入置于同一原子事务中，保证了分值与流水账的绝对强一致性。

另一项核心挑战是满座候补排队与自动递补引擎的构建。当自习室目标时段满座时，学生可提交先到先得的候补排队。我设计了基于事件驱动与条件轮询的“空位先到先得自动递补算法”：一旦因签退、取消或违约释放出座位，系统即刻触发递补引擎，按 `created_at ASC` 扫描队列；若队首学生因其他预约发生时段冲突，系统智能跳过并向后顺延，成功递补后自动创建预约单并通过站内信下发通知。通知服务采用异步非阻塞设计，避免任何通知异常反向影响核心交易。前端开发中，我开发了 `WaitlistView.vue` 实时展示排队位次动态预测，开发了抽屉式通知中心支持未读角标与一键已读。通过这套全栈机制的落地，我深刻领悟到软件系统不仅是代码的堆叠，更是解决现实业务规则与管理难题的有力工具。

### 5.2.4 邹字（学号：2404060319，主责模块四：统计与可视化模块）

我主责模块四（统计与可视化模块）的垂直全栈研发，核心攻坚方向为自习室海量历史预约数据的多维聚合分析、空间占用热力图矩阵计算、运营数据大屏、WebGL Three.js 3D 选座全景探索以及 Redis 旁路缓存防雪崩优化。

在数据聚合方面，为了直观反映自习室的时空占用特征，我设计了座位 × 小时空间占用热力图算法。在 SQL 端利用 `generate_series` 按开闭馆时段生成连续时间轴，结合 `EXISTS` 子查询与 `tsrange` 范围重叠操作符精准计算各座位小时状态；为解决统计聚合查询开销大、容易在高峰期引发数据库压力的问题，我设计了 Cache-Aside 旁路缓存架构，并在基础 TTL（3 分钟）上创新引入了 ±10% 的随机抖动（Jitter），将缓存过期时间打散在 162~198 秒之间，成功杜绝了热点缓存同时失效引发的雪崩隐患。

在前端交互维度，我致力于为学生带来沉浸式的人机交互体验。我利用 Three.js 在浏览器端实时构建了自习室 3D 三维虚拟空间，真实呈现了地板、桌椅、采光窗户与电源排布，并支持俯瞰全景、第一人称采光体验以及区域聚焦三种视角自由漫游；结合 GSAP 动效库，实现了 2D 平面选座图与 3D 沉浸式场景之间的丝滑转场过渡。在数据大屏开发中，基于 ECharts 绘制了使用率趋势折线图、高峰时段柱状图与热门座位 Top 榜，为自习室管理人员的排班与资源调配提供了坚实的数据支撑。这次全栈经历极大提升了我在高性能复杂 SQL 优化、缓存高可用架构以及 WebGL 3D 渲染领域的综合实战能力。

### 5.2.5 王建东（学号：2404060309，主责模块五：AI 助手与运维模块）

在本次课程设计中，我主责模块五（AI 助手与运维模块）的垂直全栈研发，同时担任全组的测试架构师与 DevOps 运维负责人，主笔全套测试文档与管理计划。

在 AI 助手研发上，针对大语言模型接入传统业务系统容易超时以及模型幻觉可能引发误操作的两大风险，我确立了“只读业务快照上下文 + 确定性卡片二次核验”的系统性架构原则：
1. 前端开发了全局悬浮球对话交互组件（`AIAssistant.vue`），基于标准 Server-Sent Events（SSE）协议实现了 OpenAI 兼容的打字机流式输出；
2. 服务端在收到学生消息时，一次性并行提取本人档案、信用、活跃预约、候补记录及当前自习室座位属性快照注入单次 Prompt，严格实现“一问一答一次调用”，彻底杜绝长链多轮网络往返造成的等待超时；
3. 当模型通过 `recommend_seats` 给出自然语言推荐时，后端实施严格的时段重叠物理过滤，以结构化 card 事件推送至前端；学生点击卡片二次确认后，严格调用模块二的标准预约接口，重新经过分布式锁与排除约束物理校验，坚决不赋予 AI 任何直接改库的业务特权。

在运维与工程保障方面，我基于 Redis 固定窗口计数器设计了全站 API 分布式限流中间件（`ratelimit.go`），对登录防爆破、预约接口与 AI 对话实施分级流量控制；利用 Redis 分布式锁实现了高可用巡检调度器（`scheduler.go`）的 Leader 选举主备切换，保证分布式部署下的任务单点执行；搭建了 Docker Compose 生产编排与 GitHub Actions CI/CD 流水线。此外，我统筹搭建了覆盖 22 项单元测试、23 项 E2E 接口测试与 20 线程并发抢座压测的三层金字塔自动化测试体系，用坚实客观的测试数据为系统的成功交付提供了全方位质量背书。

## 5.3 待改进之处与演进方向

在充分总结项目收获的同时，我们也客观梳理了系统当前的局限性并明确了未来的演进方向：

1. **通知渠道多通道扩展**：当前系统消息通知主要基于站内信流转，后续可进一步封装 Webhook 适配器，扩展对接企业微信、钉钉机器人以及校园统一短信网关，提升时效性通知的触达率；

# 1．引言

## 1.1 编写目的

为明确"智能共享自习室预约系统"的软件需求、安排项目规划与进度、组织软件开发与测试，特编写本需求规格说明书。

本文档的预期读者为：项目组长、各模块全栈开发人员、质量保障人员以及课程设计指导教师。本文档将作为系统概要设计、详细设计、测试计划编制的输入，以及最终系统验收的依据之一。

## 1.2 项目背景

a. **委托单位、开发单位与主管部门**：本项目为《系统分析与设计》课程设计课题，由课程设计小组（5 人）自主选题、自主开发，指导教师所在课程组为业务主管部门。开发团队采用「5 大功能模块垂直全栈分工」模式开展系统分析、设计与实现，各模块负责人统筹本模块前端交互、后端服务、数据模型与测试验证工作。

b. **系统与其他系统的关系**：本系统为独立 B/S 架构 Web 应用，不依赖外部业务系统；对外仅依赖标准网络与浏览器环境。系统面向高校共享自习室场景，向前来自习的学生提供座位查询、预约、签到等服务，向管理员提供座位资源管理与运营统计服务。

**现状与问题**：调研发现，传统自习室管理存在以下痛点——

1. **信息不透明**：学生无法提前得知自习室空位情况，往返奔波"找座"时间成本高；
2. **占座严重**：物品占座导致座位名义占用、实际闲置，资源利用率低；
3. **爽约无成本**：预约后不到场没有任何约束，座位被无效锁定；
4. **管理粗放**：管理员缺乏数据支撑，无法量化了解各时段、各区域的座位利用情况；
5. **分配低效**：高峰期人工引导分配座位秩序混乱，体验差。

本系统通过"在线选座 + 智能分配 + 信用治理 + 数据可视化"四位一体的方案解决上述问题。

# 2．任务概述

## 2.1 目标

**总体目标**：建设一套面向高校共享自习室的智能座位预约与管理平台，实现座位资源的在线化、公平化、数据化管理，提升座位利用率与学生自习体验。

**具体目标**：

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 在线预约 | 学生可按日期、时段、自习室在线选座预约，杜绝盲目找座 |
| G2 | 智能分配 | 系统按用户偏好（区域/电源/靠窗）自动推荐并分配最优座位 |
| G3 | 全生命周期管理 | 预约"待签到→签到→使用→签退"全流程线上化，超时自动违约处理 |
| G4 | 信用治理 | 违约扣分、履约加分、低分限约，从机制上抑制爽约与占座 |
| G5 | 满座候补 | 目标时段满座时可排队候补，空位释放自动递补并通知 |
| G6 | 数据可视化 | 提供座位热力图、使用率趋势、高峰时段等运营统计 |
| G7 | 消息通知 | 预约成功、违约警告、候补递补等关键事件站内通知 |

## 2.3 条件与限制

1. **进度约束**：课程计划周期为 2026-09-01 至 2026-09-15，包含分析、设计、实现、验证和答辩交付；
2. **人力约束**：5 人课程设计小组，均为在校学生，非全职投入；

## 3.3 数据库介绍

采用 **PostgreSQL 18** 关系数据库，库名 `studyroom`，启用 `btree_gist` 扩展以支持时段排他约束。共 9 张核心表：`users`（用户）、`rooms`（自习室）、`seats`（座位）、`reservations`（预约）、`credit_logs`（信用流水）、`waitlist`（候补）、`notifications`（通知）7 张业务表，以及 AI 助手专用的 `ai_conversations`（会话）与 `ai_messages`（消息）2 张表（由迁移脚本 `002_ai_assistant.sql` 建立）。

| location | VARCHAR(200) | — | 位置描述 |
| open_time / close_time | TIME | close > open | 开放时段 |
| seat_rows / seat_cols | INTEGER | 1–30 | 平面图行列规模 |
| description | TEXT | — | 房间说明 |

**（3）seats 座位表**

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| id | BIGSERIAL | 主键 | 座位标识 |
| room_id | BIGINT | 外键→rooms，级联删除 | 所属房间 |
| seat_no | VARCHAR(20) | 房间内唯一 | 座位号（如 A01） |

| zone | VARCHAR(30) | quiet/regular/discussion/computer | 功能区域 |

| near_window | BOOLEAN | 默认 false | 是否靠窗 |
| status | VARCHAR(20) | available/maintenance/disabled | 座位状态 |

**（4）reservations 预约表**

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| id | BIGSERIAL | 主键 | 预约单标识 |
| user_id / seat_id | BIGINT | 外键，级联删除 | 所属用户/座位 |
| res_date | DATE | 非空 | 预约日期 |
| start_time / end_time | TIME | end > start | 起止时间 |
| status | VARCHAR(20) | 六态枚举 | 当前状态 |
| source | VARCHAR(20) | manual/auto/waitlist | 预约来源 |
| checkin_at / checkout_at / leave_at | TIMESTAMPTZ | 可空 | 签到/签退/离开时间戳 |
| — | 排除约束 | 见下 | 时段冲突防护 |

排除约束（数据库层兜底，双保险）：

- `excl_seat_overlap`：同一座位同一天的**活跃预约**时段不得重叠；
- `excl_user_overlap`：同一用户同一天的**活跃预约**时段不得重叠（防止一人多占）。

**（5）credit_logs 信用流水表**：id、user_id（外键）、delta（分值变动，正加负减）、reason（事由）、reservation_id（关联预约，可空）、created_at。

**（6）waitlist 候补表**：id、user_id、room_id、res_date、start_time/end_time、偏好（zone/has_power/near_window，均可空）、status（waiting/promoted/cancelled/expired）、created_at。同一房间同一时段按 created_at 先后排队。

**（7）notifications 通知表**：id、user_id、type（六类事件枚举）、title、content、is_read、created_at。

**（8）ai_conversations AI 会话表**：id、user_id（外键→users，级联删除）、title（默认"新对话"）、created_at、updated_at。索引 `(user_id, updated_at DESC)` 支撑会话列表按最近活跃排序。

**（9）ai_messages AI 消息表**：id、conversation_id（外键→ai_conversations，级联删除）、role（system/user/assistant/tool）、content、tool_calls（JSONB，兼容 OpenAI 工具调用）、tool_call_id、status（streaming/complete/failed）、created_at。索引 `(conversation_id, created_at, id)` 保证消息按序回放；仅 `complete` 状态消息进入后续模型上下文。

## 3.5 数据采集

1. **管理端录入**：房间与座位由管理员创建/批量生成，形成静态资源数据；
2. **用户注册采集**：注册时采集用户名、口令（哈希）、姓名、学号；
3. **行为自动记录**：预约创建、签到、签退、取消等操作由系统自动写入对应表并维护时间戳；
4. **调度器采集**：后台定时任务扫描超时未签到预约，自动产生违约记录与信用流水；
5. **统计聚合**：热力图与统计报表由历史预约数据按"座位 × 小时"聚合生成，无需人工上报。

# 7．其它需求

## 7.1 安全保密

1. 口令仅存 bcrypt 哈希（cost=10），任何接口/日志不得出现明文口令；
2. 会话采用 JWT（HS256，24 小时有效），签名密钥环境变量注入；登出时按令牌剩余有效期写入 Redis 黑名单，实现主动注销；
3. RBAC：管理端接口仅 admin 角色可访问；AI 助手接口仅 student 角色可访问，会话按 user_id 隔离；
4. 全部 SQL 采用参数化查询，防 SQL 注入；前端输入做长度与格式校验，防 XSS；
5. AI 接口的模型密钥、系统提示词与其他用户数据不得返回前端；日志不记录提示词和业务快照；
6. 敏感端点（登录、预约、自动分配、AI 对话）挂载 Redis 限流中间件，超阈值返回 429；
7. 当前开发配置允许任意来源，正式部署前应收紧为可信来源白名单。

## 7.2 可维护性

1. 系统基于 5 大核心业务模块垂直全栈划分，模块内部按 handler / service / repository 分层解耦，边界清晰；
2. 数据库变更通过迁移脚本管理（001_init.sql、002_ai_assistant.sql），可重复执行；
3. 关键业务（分配算法、时段校验、信用规则、缓存抖动、分布式锁、限流）配套单元测试，CI 自动执行；
4. 统一结构化日志，便于排障；Redis 不可用时按用途差异化降级。

## 7.3 可移植性

1. 后端为静态编译的 Go 程序，可部署于任意 Linux 环境，具备容器化条件；
2. 数据库采用标准 SQL 与 PostgreSQL 特性（排除约束），迁移成本可控；
3. 前端构建产物为静态资源，可由任意 Web 服务器托管；
4. 运行配置全部经环境变量注入（根目录 `.env` 统一维护），可在不同环境间迁移。

## 7.4 可使用性

1. 座位平面图直观呈现占用状态，另提供 3D 座位探索视图与偏好动效反馈，预约操作 ≤ 3 步；
2. 自动分配提供推荐理由，增强可解释性与信任感；
3. 关键结果（预约成功、违约、递补）均有即时消息反馈；
4. AI 助手支持自然语言查数与选座推荐，推荐结果必须二次确认，避免误操作。

## 3.0 AI 助手总体设计

AI 助手作为模块五（AI 助手与运维模块，负责人：王建东）的核心业务子系统，由前端 Vue 悬浮组件、AI HTTP/SSE 适配层、上下文组装服务、OpenAI 兼容流式客户端和 PostgreSQL 会话仓储构成。上下文服务按 JWT 用户 ID 读取本人资料、信用、预约、候补和通知，并组合房间及座位数据；模型只生成简短文本或调用只读 `recommend_seats` 工具。工具结果经后端检查日期、时段、座位状态和实时占用后才作为卡片发送。最终预约由用户确认并复用预约服务，AI 无业务写权限。

## 3.1 处理流程

系统总体处理流程为"请求—限流—认证—防重—业务—缓存/落库—调度闭环"：
1. 浏览器发起 HTTPS/HTTP 请求；
2. 接入层 Gin 路由与中间件链：CORS 处理 → 限流中间件（基于 Redis 限制敏感接口频次）→ JWT 认证（含 Redis 黑名单校验）→ RBAC 权限判定；
3. handler 解析与校验参数；
4. service 执行业务规则：
   - 读请求优先通过 `rediscache` 检索 Redis 旁路缓存，命中则极速返回；未命中时查库并防雪崩（随机 TTL）回填；
   - 预约/释放等高并发写请求，优先通过 `redissync` 获取分布式细粒度互斥锁（如 `lock:seat:<id>:<date>`），防止并发超卖，并执行数据库事务；事务提交后主动失效相关房间和统计缓存；
5. repository 参数化访问 PostgreSQL 18，依赖 GiST 排除约束最终兜底；
6. 统一格式返回响应；同时后台调度器通过 Redis 分布式锁完成主备选举，周期运行违约扫描、候补递补与签到提醒。

# 6．运行设计

## 6.1 运行模块的组合

启动组合：`cmd/server` → 加载配置 → 建立 PostgreSQL 连接池 → 建立 Redis 客户端连接池（连通性自检） → 装配 repository → 装配 service（注入 Cache 与 Lock 组件） → 注册路由与限流中间件 → 启动 HTTP 监听 → 启动调度器 goroutine（带主备选举机制）。

运行期并发组合：每个 HTTP 请求一个 goroutine（Gin 管理）；调度器独立 goroutine，每 60 秒执行一轮（基于 Redis 锁竞选 Leader → 违约扫描 → 候补递补 → 签到提醒）。

## 6.2 运行控制

- 配置通过环境变量注入（STUDYROOM_PORT / STUDYROOM_DB_URL / STUDYROOM_JWT_SECRET / STUDYROOM_REDIS_ADDR / STUDYROOM_REDIS_PASSWORD / STUDYROOM_REDIS_DB，以及 AI 相关的 STUDYROOM_AI_BASE_URL / AI_API_KEY / AI_MODEL / AI_CONNECT_TIMEOUT_SECONDS / AI_RESPONSE_TIMEOUT_SECONDS / AI_CONTEXT_MESSAGES）；
- 统一在仓库根目录 `.env` 维护（模板 `.env.example`），后端启动时自动读取，Docker Compose 亦读取同一文件；
- `/api/health` 暴露存活状态（含 PostgreSQL 数据库连通性）；
- 收到 SIGINT/SIGTERM 优雅关闭：停止调度器 → 关闭 HTTP → 释放 Redis 连接 → 释放数据库连接池。

## 6.3 运行时间

调度周期为 60 秒。其他接口响应时间和吞吐能力需在目标部署环境通过专项性能测试确认，本说明书不记录未经复测的数值。

# 7．出错处理设计

## 7.1 出错输出信息

统一响应 `{code, message, data}`；HTTP 状态码与业务场景映射：

| HTTP | 场景 | message 示例 |
| --- | --- | --- |
| 400 | 参数错误 | 开始时间必须早于结束时间 |
| 401 | 未认证/令牌已注销/过期 | 令牌无效、已注销或已过期 |
| 403 | 无权限/禁约/禁用 | 信用分过低，暂时禁止预约 |
| 404 | 资源不存在 | 座位不存在 |
| 409 | 冲突/并发争抢 | 该座位此时段已被预约，或正在被他人预约，请稍后重试 |
| 429 | 频次超限 | 请求过于频繁，请稍后再试 |
| 500 | 内部错误 | 服务内部错误，请稍后重试 |

## 7.2 出错处理对策

1. **事务回滚**：预约创建+信用变动等多表写操作置于同一数据库事务，失败整体回滚；
2. **约束兜底**：分布式互斥锁先行排队并发请求，数据库排除约束最终兜底（409 语义转换）；
3. **Redis 优雅降级（Fallback）**：
   - 启动期如未配置 Redis 或 Redis 宕机，系统自动切换为纯数据库降级模式，并在日志中输出警告，不中断核心业务；
   - 运行期若 Redis 发生瞬时故障，缓存读取失败时相关服务回源数据库；预约锁获取发生 Redis 错误时记录日志并依赖 PostgreSQL 排除约束兜底；认证黑名单查询错误时记录日志并继续校验后的请求；注销操作因无法写入黑名单而返回 503；调度器运行中无法取得 Redis 选主锁时跳过本轮；
4. **降级运行**：统计接口异常不影响预约主链路；通知写入失败仅记日志不阻断主流程；
5. **恢复与再启动**：服务无本地状态，重启即恢复；调度任务幂等（状态条件更新），重复执行无副作用。

# 8．安全保密设计

1. 口令 bcrypt（cost=10）存储，杜绝明文/可逆加密；
2. JWT HS256，密钥经环境变量注入，令牌含 uid/role/过期时间，有效期 24h；
3. JWT 主动注销黑名单：用户退出登录或被封禁时，将 Token 哈希存入 Redis 并设置等于 Token 剩余有效期的 TTL，中间件实时校验，彻底解决 JWT 无法提前作废的安全缺陷；
4. 接口级防刷与限流：敏感端点（如登录、提交预约）挂载 Redis 计数器/滑动窗口中间件，超过阈值直接阻断（429 Too Many Requests），防范暴力破解与恶意抢座；
5. RBAC：`/api/admin/**` 强制 admin 角色，中间件统一拦截；
6. SQL 全参数化（pgx 占位符），杜绝字符串拼接；
7. 日志脱敏：口令字段永不落日志；
8. 开发配置允许任意来源跨域，正式部署前需配置来源白名单。

# 3．程序描述

## 3.1 模块一：用户与权限模块详细设计（负责人：赵晨曦）

### 3.1.1 模块概况与程序单元构成
- **定位**：负责全系统用户身份标识、注册准入、安全登录、JWT 会话管理、主动注销黑名单拦截、RBAC 角色权限控制以及管理端用户状态治理。
- **前端资产**：`views/LoginView.vue`、`views/ProfileView.vue`、`views/admin/AdminView.vue`（用户管理部分）、`stores/auth.js`、`api/auth.js`、`router/index.js`（路由守卫）。
- **后端资产**：`handler/auth.go`、`handler/admin_user.go`、`service/auth.go`、`middleware/auth.go`、`repository/user.go`、`model/user.go`、`model/claims.go`。
- **数据与缓存**：PostgreSQL `users` 表，Redis 黑名单键 `studyroom:auth:blacklist:<token_hash>`。

### 3.1.2 身份认证与密码安全算法
- **口令安全**：采用自适应哈希算法 `bcrypt(cost=10)`。用户注册与修改口令时单向哈希存储，数据库不存任何明文口令；比对通过 `bcrypt.CompareHashAndPassword` 执行。
- **会话令牌**：基于 `golang-jwt/jwt/v5` 采用 HS256 对称签名算法签发 JWT。Payload 封装 `user_id`、`username`、`role`、`student_no` 等 Claims，标准有效期设定为 24 小时（1440 分钟）。
- **认证中间件**：`JWTMiddleware` 拦截请求头 `Authorization: Bearer <token>`，解析 Claims 并注入 Gin 上下文（`c.Set("userId", ...)`、`c.Set("role", ...)`）；无 Token 或解析失败返回 401 Unauthorized。

### 3.1.3 JWT 主动注销黑名单拦截机制（Redis 组件）
- **设计背景**：针对传统无状态 JWT 无法提前注销或封禁的业界痛点，本系统在用户调用 `/api/auth/logout` 或管理员封禁用户时实现主动吊销。
- **算法与逻辑**：
  1. 服务端解析 Token 得到过期时间戳 `exp`，计算剩余生存时间：`remaining_ttl = exp - now()`；
  2. 计算 Token 的 SHA-256 哈希作为紧凑型 Redis Key：`studyroom:auth:blacklist:<token_hash>`；
  3. 执行 `SET studyroom:auth:blacklist:<token_hash> "1" EX remaining_ttl` 存入 Redis；
  4. `JWTMiddleware` 中间件在每次验证 JWT 签名通过后，额外执行 `EXISTS studyroom:auth:blacklist:<token_hash>`；若命中黑名单则直接返回 401（"令牌已注销或已失效"），实现毫秒级会话阻断。
- **优雅降级**：Redis 离线或查询异常时，中间件记录降级警告日志并依据 JWT 本身签名放行正常业务请求，保障服务高可用。

### 3.2.2 房间与座位管理及批量生成算法
- **批量生成算法**：管理员录入房间规模（行数 $R \in [1, 30]$，列数 $C \in [1, 30]$），系统按规则矩阵自动赋权：
  - 座位编号：行字母 + 列序号（如 A01 ~ Z30）；
  - 属性规约：偶数列带电源（`has_power=true`）；最右列靠窗（`near_window=true`）；前 $1/3$ 行划归静音区（`quiet`），其余为普通区（`regular`）或研讨区（`discussion`）；
  - 幂等校验：同一房间已存在座位时禁止重复批量生成（返回 409）。
- **缓存策略**：房间列表读请求优先经由 `studyroom:cache:rooms` 获取；房间或座位发生写操作时，主动失效对应缓存。

### 3.2.3 预约核心引擎与三层防超卖互斥机制
为在高并发选座场景下实现极致性能与 100% 零超卖保障，叶泳言设计了业界领先的“三层并发互斥防御体系”：
1. **第一层：Redis 细粒度分布式互斥锁（`internal/pkg/redissync`）**
   - **锁键粒度**：`studyroom:lock:seat:<seat_id>:<date>`（细粒度锁定具体座位及日期）；
   - **加锁原子性**：采用 `SET key uuid NX EX 30` 原子指令，获取成功后返回 UUID 签名解锁闭包；
   - **看门狗续期（Watchdog）**：后台启动看门狗协程，每 10 秒（TTL 的 $1/3$）对锁执行一次续期；
   - **Lua 原子解锁**：释放锁时采用比对 UUID 的 Lua 脚本，杜绝因慢业务超时导致的误删他人锁故障：
     ```lua
     if redis.call("get", KEYS[1]) == ARGV[1] then
         return redis.call("del", KEYS[1])
     else
         return 0
     end
     ```
   - **优雅降级**：Redis 宕机或网络分区时，`TryLock` 输出告警日志并安全放行，由后续层兜底。
2. **第二层：应用层 HasConflict 冲突预检**
   - 在应用事务开启前，先执行只读 SQL 查询该座位在目标时段 $[start, end]$ 内是否存在状态属于 `pending`、`checked_in`、`temp_leave` 的活跃预约。若存在，提前阻断并释放分布式锁，减轻底层数据库负担。
3. **第三层：PostgreSQL GiST 排除约束物理兜底（Exclusion Constraints）**
   - 在数据库物理层通过 `btree_gist` 扩展建立强排他约束：
     - `excl_seat_overlap`：同一座位、同一日期的活跃预约时段（`tsrange`）绝对排他；
     - `excl_user_overlap`：同一用户、同一日期的活跃预约时段绝对排他（防一人多占）；
   - 任何并发竞争漏网请求将触发数据库唯一的 `23P01` 错误码，由后端的全局错误捕获转译为友好的 HTTP 409 业务提示。

### 3.2.4 智能加权自动分配算法与热度均衡模型
- **候选集过滤**：检索目标房间与时段内所有可用且无时段冲突的座位集合 $\mathcal{S}_{cand}$。
- **纯函数加权评分模型（ScoreCandidates）**：
  $$\text{Score}(s) = S_{zone}(s) + S_{power}(s) + S_{window}(s) - 20 \times U_{7d}(s) + \text{rand}(0, 1)$$
  - 偏好匹配得分：区域符合加 30 分；电源符合加 25 分；靠窗符合加 15 分；
  - 热度均衡因子（$-20 \times U_{7d}$）：计算该座位近 7 日历史利用率，对热门座位扣减分数，将人流智能引导分散至冷门座位，实现自习室资源的“削峰填谷”；
  - 随机微扰项：引入 $[0, 1)$ 微扰打破同分僵局。
- **一键分配流转**：降序排序取 Top-N；若指定 `auto_book=true`，则直接取第一名进入三层锁预约通道创建预约。

### 3.2.5 预约生命周期有限状态机与时序控制
- **六态流转驱动**：
  - `pending`（待签到）：预约创建后的初始状态；
  - `checked_in`（使用中）：在签到窗口内通过签到接口触发；

- **状态迁移与时钟窗口**：
  - 签到窗口：$[T_{start} - 15\text{min}, T_{start} + 15\text{min}]$；
  - 状态流转执行严格原子条件更新：`UPDATE reservations SET status = :new WHERE id = :id AND status = :expected`；
  - 释放回调联动：状态变为 `completed`、`cancelled`、`violation` 时释放座位占用，主动清除关联房间及热力图缓存，并向候补模块广播空位释放事件。

### 3.4.2 运营数据聚合流水线与高性能统计算法
- **统计数据口径**：
  $$\text{利用率} = \frac{\sum \text{占用小时数}}{\text{总可用座位数} \times \text{每日开放小时数}} \times 100\%$$
  仅 `completed`、`checked_in`、`temp_leave`、`violation` 四类实质占用座位的预约计入分子。
- **核心聚合查询**：
  - 近 $N$ 天使用率趋势：按日期分组统计利用率变化，生成趋势折线；
  - 高峰时段分布：按 08:00~22:00 各小时区间分组累加占用人次，生成高峰柱状图；
  - 热门座位 Top-10：按座位维度聚合预约频次与累计占用时长，识别黄金自习区域。

### 3.4.3 空间占用热力图矩阵计算算法
- **时空矩阵构建**：针对管理员选定的房间与日期，SQL 使用 `generate_series` 生成从开馆到闭馆的 1 小时连续时间步进；
- **重叠检测**：通过 `EXISTS` 关联子查询与 PostgreSQL `tsrange` 重叠操作符判定各座位在该小时的占用状态；
- **矩阵格式输出**：后端输出二维数组 `cells[seat_idx][hour_idx]`，前端由 ECharts 热力图渲染为色彩渐变矩阵，一眼洞察冷热区域。

### 3.4.4 Redis 旁路缓存防雪崩与 Jitter 抖动设计（`internal/pkg/rediscache`）
- **Cache-Aside 机制**：统计分析接口查询开销较大，首次请求查库计算后存入 Redis，后续读请求直接从 Redis 极速反序列化返回；
- **防雪崩随机抖动（Jitter）**：基础 TTL 设为 3 分钟（180 秒），写入时动态叠加 $\pm 10\%$ 随机抖动时间：
  $$\text{ActualTTL} = \text{BaseTTL} \times (1 + \text{rand}(-0.1, +0.1)) \in [162\text{s}, 198\text{s}]$$
  打散同一时刻生成的各类统计指标过期点，有效杜绝缓存集中失效引发的数据库击穿与雪崩；
- **主动失效保证一致性**：预约状态落库或座位变更时，调用 `DeletePrefix("studyroom:cache:stats:")` 立即清理相关失效缓存。

### 3.4.5 Three.js 3D 座位探索视图与 GSAP 动效整合
- **3D 场景建模**：采用 Three.js 在浏览器端实时构建三维空间模型，包含地板、墙面、采光窗户、电源插座及自习桌椅；
- **多视角探索交互**：支持三种漫游视角切换：① 全景俯瞰（鸟瞰整体布局）；② 学生第一人称视角（体验真实入座采光与空间感）；③ 区域聚焦视角（研讨区/静音区特写）；
- **GSAP 动效整合**：在 2D 平面选座图与 3D 沉浸式场景切换时，利用 GSAP 动画引擎实现平滑淡入淡出与相机平移插值，消除生硬跳变。

### 3.5.2 AI 智能对话与统一业务上下文组装
- **架构原则**：AI 助手采用只读上下文设计，定位为学生的贴身导学与助约参谋，严禁赋予模型直接写入预约的业务权限。
- **单次模型调用组装机制**：
  - 学生发起对话时，后端按 JWT 提取该用户 ID；
  - 服务端一次性并行提取：本人资料、信用分、活跃预约单、候补位次、未读消息，以及全自习室可用房间与座位属性列表；
  - 组装为高密度结构化业务快照，注入单次会话 System Prompt；
  - 每条用户消息最多触发一次模型调用，彻底杜绝多轮网络往返造成的等待与超时。

### 3.5.3 OpenAI 兼容流式客户端与推荐卡片二次核验
- **SSE 流式传输**：采用 Server-Sent Events 标准协议，向前端增量推送打字机事件流：
  - `meta`（返回会话 ID 等元数据）、`delta`（文字流式增量增量切片）、`card`（结构化推荐卡片载荷）、`done`（流结束标识）、`error`（异常通知）；
- **推荐卡片后端核验**：
  - 当模型通过工具调用 `recommend_seats` 输出推荐方案时，后端拦截参数并进行严格物理校验：时段是否符合房间开放时间、目标座位是否已被活跃预约抢占；
  - 校验通过后，筛选出最多 3 个真实可约座位封装为 `card` 事件推送至前端；
- **二次确认预约闭环**：前端推荐卡片展示“立即预约”操作，点击后弹出核验对话框，确认后调用标准 `POST /api/reservations` 接口，完整复用模块二的分布式锁、冲突校验与排除约束，实现 AI 推荐与确定性安全预约的无缝衔接。

### 3.5.4 定时巡检调度器与分布式 Leader 选举（`internal/service/scheduler.go`）
- **分布式主备选举**：
  - 多节点部署环境下，为防止重复扫描，调度器每轮执行前向 Redis 申请分布式锁：`studyroom:scheduler:leader`（TTL 30 秒，看门狗 10 秒续约）；
  - 仅竞选成功为 Leader 的实例执行定时巡检任务，其余 Follower 实例跳过本轮，保障任务单点执行；
  - 当 Redis 离线时，自动降级为单机本地定时器安全运行。
- **60 秒巡检任务链**：
  1. 超时未签到扫描：扫描 `pending` 且当前时间已超签到窗口（开始 + 15min）的预约，原子更新为 `violation`，触发扣减信用分 8 分并广播释放事件；
  2. 到时自动完成：扫描 `checked_in` / `temp_leave` 且当前时间已过结束时间的预约，更新为 `completed` 并给予履约加分；
  3. 暂离超时处理：扫描 `temp_leave` 超过 30 分钟的记录，置为提前签退；
  4. 候补排队自动推进：对本轮释放的所有空闲时段触发候补递补引擎；
  5. 签到提醒推送：对即将进入签到窗口（开始前 15 分钟）的用户下发站内提醒。

### 3.5.5 分布式 API 限流中间件（`internal/middleware/ratelimit.go`）
- **固定窗口计数器模型**：利用 Redis 原子指令 `INCR` 与 `EXPIRE` 构建轻量级限流防刷门禁；
- **全站关键端点分级防护**：
  - 登录接口：限制每 IP 每分钟最多 10 次（防密码爆破）；
  - 预约与自动分配：限制每用户每秒最多 2 次（防自动化抢座脚本）；
  - AI 对话流式接口：限制每用户每分钟最多 10 次（防大模型 API 额度滥用）；
- **阻断策略**：计数器超阈值时立即中断调用链，统一返回 HTTP 429 Too Many Requests。

### 3.5.6 测试保障体系与 CI/CD 运维
