## 5 技术难题攻关与复盘总结

在 15 天的高强度研发与全栈实现过程中，团队遇到并攻关了以下五大关键技术挑战：

### 5.1 难点一：高并发抢座防超卖与一致性保障
- **问题表征**：自习室选座属于典型的高并发强一致性场景。若仅在应用层做先查询后插入（Check-Then-Act），高并发下极易出现脏读导致同一座位同一时段被多人预约。
- **攻关方案（叶泳言、王建东）**：
  1. 第一层：Redis 细粒度互斥锁（`studyroom:lock:seat:<seat_id>:<date>`），利用 SETNX + UUID 属主 + Lua 原子释放脚本，结合后台协程看门狗自动续租，实现毫秒级排队；
  2. 第二层：应用层冲突预检，阻断不合规时段或已存在预约；
  3. 第三层：PostgreSQL 物理层 GiST 排除约束兜底（`EXCLUDE USING gist (seat_id WITH =, reservation_range WITH &&)`），由数据库内核在事务提交时保证时间区间物理排他。
- **验证成果**：20 线程并发压测下，严格实现 1 笔成功、19 笔被排他拦截、0 超卖。

### 5.2 难点二：无状态 JWT 会话的主动注销问题
- **问题表征**：标准 JWT 令牌为客户端无状态持有，用户执行“退出登录”后，在令牌未自然过期前依然可以携带该 Token 访问受保护端点，存在安全隐患。
- **攻关方案（赵晨曦）**：
  引入 Redis 旁路黑名单机制（`studyroom:auth:blacklist:<token_hash>`）。用户主动退出时，计算当前 JWT 距离自然过期的剩余时间（TTL），以该时间写入 Redis 黑名单；在 Gin 鉴权中间件解析有效 Claims 后，先以 $O(1)$ 复杂度查询 Redis，若命中则直接返回 401 Unauthorized。同时设计了 Redis 连接异常时的策略降级机制。

### 5.3 难点三：AI 智能助手的安全性与业务边界隔离
- **问题表征**：大语言模型存在幻觉隐患，若赋予 AI 直接调用写接口预约自习室的权力，极易引发越权预订、虚假预约或规则绕过。
- **攻关方案（王建东）**：
  严格确立“**AI 只读上下文注入 + 建议性推荐 + 前端用户显式二次确认**”的安全闭环。系统仅向模型 prompt 注入当前学生本人的预约、信用和候补上下文，模型仅以结构化 JSON 卡片形式给出推荐建议（包含推荐自习室、时段与理由）；前端接收到卡片后弹出二次确认对话框，用户点击“确认预约”后走模块二的正式预约 API 进行完整的信用、时段与分布式锁校验，坚决杜绝 AI 写库越权。

### 5.4 难点四：自习室多维统计热力图的缓存雪崩防御
- **问题表征**：运营大屏与座位热力图需要对数万条历史预约进行多维时段聚合计算，数据库开销极大。若统计缓存集中在某一整点同时失效，将导致瞬时高并发请求直接击穿数据库造成系统卡死。
- **攻关方案（邹字）**：
  构建 `pkg/rediscache/` 旁路缓存组件（Cache-Aside）。在默认设置的 180 秒（3 分钟）缓存基准过期时间上，叠加 $\pm 10\%$ 的均匀分布随机抖动时间（Jitter，即 162s ~ 198s），从概率上彻底打散热点聚合键的过期时点，消除缓存雪崩隐患；同时在座位状态发生写操作时主动按前缀失效对应房间缓存。

### 5.5 难点五：前端工程大包体积与 3D/图表渲染性能优化
- **问题表征**：前端工程引入了 ECharts 6.1 与 Three.js 0.185，初始打包时 Vite 报出超过 500KB 的大 chunk 警告，影响弱网环境加载体验。
- **攻关方案（邹字）**：
  在 `vite.config.js` 中实施精细化 `rollupOptions.manualChunks` 分包配置，将 ECharts、Three.js、GSAP 及核心应用逻辑切分为独立 vendor chunk；对 3D 选座组件实行动态异步懒加载，仅在用户点击“3D 视角探索”时才异步按需载入 WebGL 场景代码，显著降低了首页加载耗时。

1. **多渠道通知扩展**：目前系统通知主要基于站内信流转，未来可对接企业微信/钉钉应用消息机器人及校园统一短信网关；
2. **硬件门禁与动态防伪**：引入动态刷新 TOTP 二维码或教室蓝牙 Beacon 广播定位，进一步杜绝远程“代打卡”与恶意占座；
3. **多校区分布式部署**：将单实例架构演进为支持多校区多租户的微服务/分布式集群，引入 PostgreSQL 读写分离与 Redis Cluster 分片支撑更大并发规模。
